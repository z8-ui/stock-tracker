## 1. 要解决的问题

以前 `buildFinancialsHtml()` 第一行是：

```javascript
if (!fin || !fin.report_date) return '';
```

财报拿不到时页面上**什么都没有**。用户无法区分：

| 实际情况 | 以前的页面 |
| --- | --- |
| 上游明确说这只股票没有财报 | 空白 |
| 财报接口超时/500 | 空白 |
| 缓存里有合法旧财报，本次刷新失败 | 空白（有时直接显示财报但不说明是旧数据） |
| 缓存被判定非法、已剔除 | 空白 |

S3-4B 的原则：**有没有财报、请求成败、缓存来源、数据新鲜度是四个不同事实，分别表达。**

## 2. 请求级状态对象

### 2.1 契约

```json
"financials_status": {
  "fetch_status":  "success | empty | failed | not_attempted",
  "served_from":   "network | memory | file | file_fallback | memory_fallback | none",
  "freshness":     "fresh | stale | unknown",
  "fetched_at":    "2026-11-12 20:27:22",      // 本次返回数据自己的抓取时间
  "report_date":   "2026-09-30",               // 财报报告期（上游 REPORT_DATE）
  "cache_rejected": false,
  "reason":        "本次抓取成功"
}
```

- `fetch_status` 只描述**本次**上游尝试：没打上游就是 `not_attempted`，绝不继承上一轮的 `failed`。
- `served_from` 描述这份数据的来源；`file_fallback` / `memory_fallback` 一定是降级。
- `freshness` 只看这份数据距自己抓取时刻有多旧（休市容忍 3 天，盘中 15 分钟）。
- `fetched_at` 与 `report_date` 是两件事：前者是本地抓取时刻，后者是财报报告期，永不互相顶替。

### 2.2 生成方式（生产代码）

`data_service.get_latest_financials(stock_code, refresh=False, trace=None)`：

- `trace` 可选，是**调用方自己的字典**；不传时行为与以前完全一致。
- 函数返回前在 `finally` 里写 `trace["status"] = _fin_build_status(trace, fin)`。
- 返回值契约不变：仍是十字段 dict 或 `None`，状态绝不塞进财报本体。
- 后台 SWR 即便在请求结束后才返回，也不会再回写已结束请求的状态（`trace["_closed"]` 哨兵），但仍然照常抓取并更新缓存。
- 模块级 `_FIN_LAST_DIAG`（`get_financials_diagnostic()`）继续存在，**只供排查**；路由与页面一律不读它。

### 2.3 状态矩阵（生产函数实测）

| 场景 | fetch_status | served_from | freshness | 返回值 |
| --- | --- | --- | --- | --- |
| 交易时段首次抓取成功 | success | network | fresh | 十字段 |
| 上游 `result.data=[]`、无缓存 | empty | none | unknown | None |
| 上游超时/连接失败、无缓存 | failed | none | unknown | None |
| 内存缓存命中（TTL 内，未请求上游） | not_attempted | memory | fresh | 十字段 |
| 文件缓存命中（休市，未请求上游） | not_attempted | file | fresh/stale | 十字段 |
| `refresh=1` 成功 | success | network | fresh | 十字段 |
| `refresh=1` 失败、有合法文件缓存 | failed | file_fallback | stale | 十字段（降级） |
| `refresh=1` 失败、只剩合法内存快照 | failed | memory_fallback | stale | 十字段（降级） |
| 缓存非法 → 淘汰 → 重抓成功 | success | network | fresh | 十字段 |
| 缓存非法 → 淘汰 → 重抓失败 | failed | none | unknown | None |
| 非法内存 + 合法文件 + 上游失败（休市） | failed | file | stale | 合法文件 |

## 4. 页面呈现

新增纯函数层 `static/js/financials_status.js`（无 DOM 依赖，可被 Node 直接执行）：

- `view(status)` → `{kind, tone, badge, message, degraded}`
- `meta(status)` → `报告期 … · 抓取 … · 来源 …`（抓取时间缺失时明确写"抓取时间未知"）

`valuation.js::buildFinancialsHtml(fin, status)` 的文案对照：

| 状态 | 页面 |
| --- | --- |
| success/network | 财报快照 + 徽标「实时抓取」 |
| not_attempted + memory/file | 财报快照 + 徽标「缓存」+ "本次未请求上游" |
| file_fallback / memory_fallback | 财报快照 + 徽标「旧数据」+ "本次财报获取失败，当前展示的是此前保存的财报（非本次抓取结果）" + 「数据已陈旧」 |
| empty + 无缓存 | "暂无财报（上游没有该股票的财报记录）" |
| failed + 无缓存 | "财报获取失败（网络或接口异常）" |
| cache_rejected 且无财报 | "财报缓存数据无效，当前无法展示" |
| 无状态字段 | "财报状态未知（接口未返回状态信息）" |

禁止项自检：不再出现 `return ''`；不会把 `fetched_at` 当报告期；不会把旧财报标成实时；
EPS=0 显示 0（不显示 `-`），EPS=null 显示 `-`。

`templates/base.html` 只加了一行 `<script src="/static/js/financials_status.js"></script>`，样式全部内联，未动全局 CSS。

## 8. r2 整改（首轮复审两项必改）

### 8.1 上游 empty + 缓存回退，不再叫"抓取失败"

问题：`refresh=1` 时 Provider 返回 `empty`，缓存层回退到合法文件缓存，`_fin_build_status()`
却统一写 "本次抓取失败，回退到文件缓存"，前端也统一显示"本次财报获取失败"——把
"上游没有这条财报记录" 说成了 "接口挂了"。

修复：

- `_fin_build_status()`：`served_from` 为 `file_fallback` / `memory_fallback` 时按
  `fetch_status` 分流 —— `empty` 用"本次上游未返回财报记录，回退到…"，
  `failed` 保持"本次抓取失败，回退到…"。
- `_fin_get_with_cache()`：内存回退分支不再无条件覆盖 `reason`（没有缓存淘汰时交给
  `_fin_build_status` 按 empty/failed 生成）。
- `financials_status.js::view()`：降级分支区分 `empty`，文案
  "本次上游未返回财报记录，当前展示此前保存的财报快照。"，并带 `empty_upstream: true`。
- 不变：`fetch_status` 保留 `empty`，`served_from` 保留 `*_fallback`，`freshness` 仍 `stale`，
  合法历史财报与原始 `fetched_at` / `report_date` 全部照旧。

前后对照见 `evidence/fix_before_after.txt`（旧代码 = 7c4ac0a，新代码 = 本轮）。

### 8.2 后台 SWR 不再污染当前请求的同步状态

问题：`fetch()` 闭包直接写 `trace["attempts"] / provider_status / provider_reason`，
而同一个 `fetch()` 也会被 `_spawn_refresh()` 在后台线程调用。此前只靠
`if not trace.get("_closed")` 兜底，挡不住"后台比前台先完成"的时序：前台返回旧内存
EPS=40，状态却被写成 `fetch_status=success`。

修复：改为**线程本地绑定** `_FIN_TRACE_LOCAL`

- `read()` 在同步取数的**本线程内**把本请求 trace 绑到 thread-local，`finally` 解绑；
- `fetch()` 只写"当前线程绑定的那个 trace"；后台 SWR 线程 thread-local 为空，
  抓到的数据照常返回给 `_spawn_refresh()` 更新缓存，但一个字都不写进前台状态；
- `_spawn_refresh()` 默认行为、6 小时 TTL、single-flight、恢复请求上限全部未动。

结果：后台先完成时，前台状态是 `not_attempted / memory / stale`（描述真实返回的旧数据），
后台成功仍会写入新财报，下一次请求正常命中新缓存。
