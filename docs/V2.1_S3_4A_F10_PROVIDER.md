### 3.1 非有限数值（r2 修正）

`NaN` / `Infinity` / `-Infinity` / 溢出（`"1e309"`，解析成 `inf`）不是财务数据。
一旦放行，会形成"财报成功 → `available=True` → 内在价值 `inf` / 偏离度 `nan`"，
而且 `json.dumps(..., allow_nan=False)` 会直接抛
`ValueError: Out of range float values are not JSON compliant`。

处理：`_num_field()` 对 `int/float` 与字符串解析结果都做 `math.isfinite()` 检查，
非有限 → `ProviderFormatError`，消息带 `field=EPSJB` 这样的原始字段名。
**不改成 0，不给默认值，不丢弃字段后继续。**

| 输入 | 结果 |
|---|---|
| `EPSJB="NaN"` / `"Infinity"` / `"-Infinity"` / `"1e309"` | failed，`field=EPSJB 不是有限数值` |
| `EPSJB=float("nan")` / `float("inf")` | failed，同上 |
| `TOTALOPERATEREVE` / `PARENTNETPROFIT` / `BPS` / `ROEJQ` 非有限 | failed，消息带各自字段名 |
| `EPSJB=0` | success，`0`（int） |
| `EPSJB=None` | success，`None` |
| `EPSJB=51.53`、`BPS=216.949629787912` | success，数值与类型不变 |
- `"-"` / `"--"` / `""` / `"null"` 这类占位符 → `None`（东财偶尔用 `-` 表示缺失）；不可解析的字符串 → `failed`，不静默变 None。

## 4. 状态语义

| 情形 | Provider 结果 | 业务返回值（`get_latest_financials`） |
|---|---|---|
| HTTP 200 + JSON + `result.data` 非空 + `data[0]` 是对象 + 日期可解析 | `success` | 十字段 dict |
| 个别指标为 null（如 EPS=null） | `success` | 十字段 dict，该项为 None |
| `result.data = []` | `empty` | `None`（不缓存） |
| `result.data = null` | `empty`（上游明确"无记录"） | `None`（不缓存） |
| `result` 缺失 / 非对象 | `failed` | `None`（不缓存） |
| `result.data` 非列表 / `data[0]` 非对象 | `failed` | `None`（不缓存） |
| `success=false`（上游报错） | `failed` | `None`（不缓存） |
| HTTP 非 200 | `failed`（`HTTP 500` 等） | `None` |
| 超时 / 连接失败 | `failed`（`ProviderTimeout` / `ProviderNetworkError`） | `None` |
| JSON 非法 | `failed`（`JSON 解析失败`） | `None` |
| `REPORT_DATE` 缺失 / 非法日期 | `failed`（消息含 `field=REPORT_DATE`） | `None` |
| 数值字段不可解析（如 `EPSJB="abc"`） | `failed`（消息含 `field=EPSJB`） | `None` |
| 数值字段非有限（NaN / Infinity / 溢出） | `failed`（消息含 `field=EPSJB`） | `None` |
| `NOTICE_DATE` = null / `""` / `"-"` / `"--"` | `success`，`notice_date=None` | 十字段 dict |
| `NOTICE_DATE` 非空但非法（如 `2026-13-01`） | `failed`（消息含 `field=NOTICE_DATE`） | `None` |

关于「empty 和 failed 都是 None」：**这是刻意的**。旧契约里业务方只认 dict 或 None，
把状态塞进十字段 dict（例如 `{"status": "empty"}`）会被估值代码当财报读。
状态在 Provider 层完整保留（`ProviderResult.status` / `.error`），页面呈现方案见 §9。

## 10. S3-4B 页面状态呈现建议（本轮未实施）

现状：`static/js/valuation.js::buildFinancialsHtml()` 在 `fin` 为 falsy 时 `return ''`，
所以"无财报"和"接口失败"在页面上都是**一片空白**，无法区分，也不满足阶段验收的
"无财报时显示无财报，而不是暂无数据"。

建议方案（不改 `financials` 本体）：

1. **状态走独立字段，不塞进财报对象**

   `/api/valuation` 的 `data` 里增加：

   ```
   "financials_status": "ok" | "empty" | "failed" | "stale",
   "financials_note":   "东财 F10 无 2026 三季报记录" / "财报接口暂不可用（超时）" / ""
   ```

   `chart["financials"]` 结构保持十字段或 null 不变。前端 `buildFinancialsHtml(fin, status, note)`
   在 `fin` 为空时按 status 输出"无财报"或"财报暂不可用"，两者文案不同、颜色不同。

2. **状态从哪来**：`data_service` 内新增 `get_latest_financials_status(stock_code)`（或让
   `get_stock_valuation` 内部同时读 Provider 状态），把 `ProviderResult.status` 映射成
   `ok / empty / failed`；`served_from=file_fallback` 时映射成 `stale`。
   老函数 `get_latest_financials()` 的返回值一个字不改。

3. **对原契约的影响**：新增字段，不删不改；旧前端忽略未知字段即可，不破坏。

4. **预计改动文件**（S3-4B 需要单独授权）：
   - `data_service.py`：状态侧通道 + `get_stock_valuation` 透传
   - `routes.py`：`/api/valuation` 增加两个字段（`/api/intrinsic-value` 可选）
   - `static/js/valuation.js`：`buildFinancialsHtml` 接收状态与文案
   - `templates/valuation.html`：可能只需一个容器 id（若走 DOM 插入则无需改）
   - `tests/`：Node 断言（empty/failed/stale 三态文案）+ Python 路由字段断言
   - 可选：`X-Financials-Status` 响应头（与 S3-3 的 `X-Data-*` 风格一致），供调试与自动化核对

5. **不建议**：把 `financials` 改成 `{"status": "empty"}`，或让 `get_latest_financials()` 返回带状态
   的 dict —— 估值代码会把它当财报读，`eps` 缺失会被误判为"无 EPS"，掩盖真实原因。

## 12. 剩余风险

1. `result.data=null` 被判为 `empty` 而不是 `failed`：东财在 `pageNumber` 越界时确实返回 `null`，
   与"没有财报"在响应里无法进一步区分；若上游改成"出错也返回 null"，会被误判成 empty。
   缓解：`success=false` 已单独判 failed；真正出错通常带 `success:false` 或非 200。
2. 日期字段从"宽松切片"改为"必须是合法日期"：`REPORT_DATE` 为空或异常字符串现在直接 failed
   （以前会得到空串继续跑）。这是有意的（结构错误不静默吞），但会让旧缓存路径下的兜底更常用。
3. **有意语义修正**：`NOTICE_DATE` 缺失时，旧实现返回 `""`，新实现返回 `None`。
   两者都是"没有披露日期"，但 `None` 与本项目其它缺失值一致。因此"所有缺失输入的返回值与旧实现
   逐字节相同"这句话**不成立**，别这样对外描述；正常有值时的逐字段一致性不受影响（10/10）。
4. `NOTICE_DATE` 非空但非法仍然 failed：本轮只放宽"缺失"，没有放宽"写错"。
5. 解析耗时增加了 `isfinite` 与类型校验，微秒级，可忽略。
6. 缓存 TTL 未变（6 小时），财报披露当天最长可能滞后 6 小时 —— 与迁移前一致，不属于本轮问题。
7. 真实上游验证只覆盖 3 只股票、单次调用（2026-11-12 19:19 由 Hermes 采集），不能证明长期稳定性；
   本轮 r2 修正全部是离线可复现的，没有重新请求上游。

## 13. r3 修正：历史缓存的数值真实性闸门

### 13.1 问题

Provider 的 `math.isfinite()` 只作用于**本次网络抓取**。`_cached_get()` 的三条读取路径
（交易时段内存命中、休市读文件、刷新失败回退文件）都不再经过 `normalize()`，
`validate_fn=lambda x: x is not None` 也拦不住 `eps=inf`。实测（真实加载 9bb82f0 的 data_service.py）：

```
修复前  缓存eps=inf     返回eps=inf     available=True  intrinsic=inf  严格JSON=ValueError 上游调用=0 缓存残留=True
修复前  缓存eps=nan     返回eps=nan     available=False intrinsic=None 严格JSON=ValueError 上游调用=0 缓存残留=True
修复前  缓存eps=51.53   返回eps=51.53   available=True  intrinsic=1374.14 严格JSON=OK      上游调用=0 缓存残留=True
```

### 13.2 处理（只在 F10 范围内，不动全局 `_cached_get`）

1. **出缓存再验一次**：`_fin_values_finite(fin)` 检查 `eps/bps/revenue/revenue_yoy/
   net_profit/profit_yoy/roe` 七个数值字段 —— `None` 或有限数值才通过，`bool`/`str`/
   NaN/Infinity 一律判无效。0 仍是合法值。
2. **同一校验也传给 `_cached_get(validate_fn=...)`**：新抓取结果与后台 SWR 刷新结果都会过这一关，
   坏数据不会被写进缓存。
3. **就地淘汰 + 有界重抓**：命中坏缓存时 `_drop_fin_cache(code)` 只删 `fin_{code}`
   （内存 / `_LAST_SUCCESS` / 文件里的该 key；不清空整份 `_data_cache.json`、不动其它 key 与板块元数据），
   然后 `force=True` 重抓**一次**。重抓成功 → 正常十字段；重抓仍失败 → 返回 `None`，
   绝不把坏值当 `file_fallback` 兜底。
4. **诊断侧通道**：`_FIN_LAST_DIAG[code] = {status, reason, cache_rejected}`，
   由 `get_financials_diagnostic(code)` 读取，供 S3-4B 页面状态呈现；不改变 `get_latest_financials()` 契约。

修复后同脚本：

```
修复后  缓存eps=inf     返回eps=None    available=False intrinsic=None 严格JSON=OK 上游调用=2 缓存残留=False
修复后  缓存eps=nan     返回eps=None    available=False intrinsic=None 严格JSON=OK 上游调用=2 缓存残留=False
修复后  缓存eps=51.53   返回eps=51.53   available=True  intrinsic=1374.14 严格JSON=OK 上游调用=0 缓存残留=True
```

（"上游调用=2"是因为脚本连续取了两次财报，每次各重抓一次；单次调用只重抓一次。）

### 13.3 新增测试（I 组，12 条）

| 测试 | 断言 |
|---|---|
| 文件缓存 `eps=inf` | 返回 None；上游被调用一次；坏条目从文件里消失 |
| 文件缓存 `inf` + 内在价值 | `available=False`、`intrinsic_value=None`、`json.dumps(allow_nan=False)` 通过 |
| 内存缓存 `eps=nan`（交易时段） | 返回 None；内存条目被淘汰 |

| 坏缓存 + 重抓成功 | 十字段完整；第二次调用 0 次上游（缓存已修复） |
| 坏缓存 + 重抓失败 | 返回 None；文件里不残留坏条目；估值不出现 nan/inf |
| 合法旧缓存 | 0 次上游请求，`report_date`/`eps` 原样 |

全量（r5 后）：**847/847 OK**（739 基线 + 108 F10），干净 Clone 同结果。

### 13.4 剩余风险

- 坏缓存是"每次取数淘汰一次 + 重抓一次"的局部策略：如果上游持续返回坏数据，
  每次请求都会多一次上游调用（有界，不会无限循环）。真正的源头已被 Provider 拦住。
- 文件缓存被淘汰后，若重抓失败，该股票在本次请求内**没有**旧财报可展示 ——
  这是有意选择（宁可不给，也不给非法值）。

## 14. r4 修正：缓存分层淘汰与有界恢复

### 14.1 边界 1：内存坏 ≠ 文件坏

r3 的 `_drop_fin_cache()` 只按"缓存里有坏值"就同时删内存、`_LAST_SUCCESS` 和文件里的该 key。
一份非法内存会把另一层**合法**文件缓存一起带走，上游又恰好不可达时，业务方就直接 None 了。

实测（同一脚本加载 r3 与 r4 的 data_service.py）：

```
边界1：非法内存 + 合法文件 + 上游失败
修复前 r3  返回eps=None   文件eps=已删除  文件保留=False 上游调用=1
修复后 r4  返回eps=51.53  文件eps=51.53   文件保留=True  上游调用=1
```

现在按层判定：

| 函数 | 作用范围 |
|---|---|
| `_fin_memory_invalid(code)` | 只看内存条目，判断是否非法（免费，读字典） |
| `_drop_fin_memory(code)` | 只删内存条目 + 它自己的 `_LAST_SUCCESS`，文件不动 |
| `_drop_fin_file(code)` | 只删 `_data_cache.json` 里的 `fin_{code}` 及其旁路元数据，内存不动 |

坏值来源由 `_cached_get(trace=...)` 的 `served` 字段判定（`memory` / `stale` / `file` /
`file_fallback` / `network`），删哪层取决于它来自哪层，不再"两层一起清"。

### 14.2 边界 2：过期坏内存不得同时触发 SWR 与同步重抓

r3 里过期内存会先被 `_cached_get()` 当成 SWR 旧数据 → 起一个后台刷新 → 返回值又被业务层
判定非法 → 强制 `force=True` 再抓一次。一次业务调用两次上游请求。

现在在进入 `_cached_get()` **之前**先摘掉明显非法的内存条目，SWR 就没有"旧数据"可返回：

```
边界2：过期非法内存（>6h TTL）+ 上游失败
修复前 r3  返回eps=None 上游调用=2 SWR刷新=1
修复后 r4  返回eps=None 上游调用=1 SWR刷新=0
```

恢复请求的上限：一次业务调用最多一次额外恢复请求；若坏值是在"本轮上游刚刚失败"之后
作为 `file_fallback` 被读到的，则只淘汰不重试（`served == "file_fallback"` 分支），
避免对着已经挂掉的上游再打一次。

### 14.3 不变的部分

- 合法内存命中：两版都是 0 次上游、0 次后台刷新（有对照）。
- 合法过期内存：仍走原来的 SWR（先返回旧值、后台刷新一次），没有被本轮的校验改成同步抓取。
- 正常 TTL（6h）、`refresh=True` 语义、缓存键、文件信封结构、板块/行情/资金流缓存全部未动。
- Provider 的 NaN/Infinity 拦截与 NOTICE_DATE 可选逻辑一个字没改。

### 14.4 新增测试（J 组，11 条）

| 测试 | 断言 |
|---|---|
| 非法内存 + 合法文件 + 上游失败 | 返回 51.53；文件仍在；`_asof` 保留原抓取时间；上游 1 次 |
| 合法内存 + 非法文件 | 命中内存 0 次上游；内存未被删；没被读到的文件未被改动 |
| 两层都非法 + 上游失败 | 返回 None；两层都被淘汰；严格 JSON 通过；仅 2 次上游（两次业务取数各 1 次） |
| 过期非法内存 | 上游 1 次、SWR 0 次 |
| 过期非法内存连续 3 次 | 每次 1 次，无内部循环放大（共 3 次） |
| 过期合法内存 | 仍触发 SWR 1 次、同步 0 次；返回旧值；校验函数能拒坏值 |
| 过期合法内存 + 刷新完成 | 后台 fetcher 返回 51.53，校验通过 |
| 坏缓存 → 失败 → 恢复 | 失败轮 None；恢复轮 51.53 并落盘；之后命中缓存不再请求上游 |
| 多 key 隔离 | 只删 `fin_600519`；`fin_000001` / `sector_flow` / `__data_meta__` 原样；合法股票 0 次上游 |
| 十字段回归 | 字段、BPS/营收精度、披露日不变 |
| 零 / None / 内在价值 | eps=0、eps=None、notice=None 均合法；内在价值 `isfinite` |

### 14.5 诊断侧通道的能力边界（S3-4B 必读）

**当前 `get_financials_diagnostic()` 不具备严格的逐请求状态绑定能力，S3-4B 不得直接将其作为页面状态来源。**

原因：它是模块级 `dict` 的"最新值"，不是随响应返回的对象。并发请求、或"上一轮失败 →
下一轮命中缓存"这种连续调用，都会让读到的人拿到别的请求留下的状态（GPT 已复现两个场景）。
本轮只做了轻量改善（每次调用开头重置，并按本次 `served` 与返回值给出
`ok / cache_hit / empty / failed / cache_rejected`），**没有**解决并发绑定问题，也没接 routes。

S3-4B 的建议方案：不要读这个全局 dict，而是在 `get_stock_valuation()` 内**现场**生成一份
状态对象，随响应一起返回，例如：

```python
# 每次请求独立构造，不共享
fin_status = {
    "status": "ok" | "empty" | "failed" | "cache_rejected" | "cache_hit",
    "served": trace["served"],          # network / memory / file / file_fallback / none
    "asof": trace.get("version"),       # 这份数据自己的抓取时间
    "reason": "…",                      # 人话原因，来自 ProviderResult.error 或缓存拒绝原因
}
```

判断顺序固定为：本次是否取得财报 → 若取得，来自网络还是缓存 → 若没取得，Provider 是
empty 还是 failed → 是否发生过缓存拒绝。页面只按这份"本次响应的状态"渲染文案，
不再猜。实现时 `get_latest_financials()` 的返回值契约保持不变，状态走并列字段或响应头。

### 14.6 剩余风险

- 坏文件缓存 + 休市场景仍需一次重抓才能恢复：如果上游不可达，本次请求没有财报（不返回坏值）。
- 每轮最多一次恢复请求，但仍会随请求次数放大（有界，不循环）。
- `_FIN_LAST_DIAG` 仍是进程级最新值，只适合排查；S3-4B 必须按 14.5 的方案重做状态通道。
- 本轮全部离线验证，未联网抓取；真实上游证据仍是更早那一次三只股票记录。

## 15. r5 修正：休市时合法内存不被坏文件遮挡

### 15.1 问题

休市读取顺序是"文件优先"。当文件缓存坏了、内存里那份是合法的，r4 的流程是：
读到坏文件 → 淘汰文件那一层 → `force=True` 重抓 → 上游不可达 → 返回 `None`。
合法内存还在，但这次请求没有用它，业务方照样拿不到财报。

实测（离线，加载 r4 与 r5 的 data_service.py）：

```
场景1 休市：合法内存 + 非法文件 + 上游失败
r4  eps=None    _asof=-      stale=None  fallback=None    内存保留=True  文件保留=False 上游=1
r5  eps=51.53   _asof=内存原始时间  stale=True  fallback=memory  内存保留=True  文件保留=False 上游=1
```

### 15.2 处理

新增两个只服务 F10 的小函数：

| 函数 | 作用 |
|---|---|
| `_fin_memory_snapshot(code)` | 读内存条目；`_fin_values_finite()` 通过才返回 `(data, ts)`，否则 `(None, None)`；不删、不改时间 |
| `_fin_memory_fallback(code, reason)` | 把合法内存快照包装成"降级数据" |

回退点只有两处，都在 F10 内部：

1. `served == "file_fallback"`（本轮上游已经失败、坏文件只是兜底）→ 淘汰坏文件后尝试内存回退；
2. 最终没有拿到财报时（休市读盘失败、force 刷新失败都走这里）→ 先尝试内存回退，再判失败。

降级数据的标记（不冒充本次成功）：

```python
out["_asof"]        = 内存条目自己的时间     # 绝不刷成 now
out["_stale"]       = True
out["_stale_reason"] = "本次抓取失败、文件缓存不可用，回退到内存中的财报快照（非本次网络结果）"
out["_fallback"]    = "memory"
out["_source"]      = "eastmoney"
```

诊断状态新增 `memory_fallback`，与 `ok / cache_hit / empty / failed / cache_rejected` 并列。

### 15.3 没变的语义

- 休市"文件优先"没有改变：两层都合法时仍返回文件那份（实测 eps=48.0、`_asof` 为文件时间、0 次上游）。
- 交易时段"内存优先"没有改变；非法内存仍被淘汰、合法文件仍可用。
- `force=True`：成功 → 返回本次新抓数据，不带 fallback 标记；失败 → 先合法文件、再合法内存，始终 1 次上游。
- 两层都非法时仍返回 `None`，不做任何形式的非法回退。

### 15.4 新增测试（K 组，9 条）

| 测试 | 断言 |
|---|---|
| 休市 合法内存 + 非法文件 + 上游失败 | eps=51.53；`_asof`=内存时间；`_stale=True`；`_fallback=memory`；内存保留；文件淘汰；上游 1 次 |
| 休市 两层都非法 | 返回 None；两层都淘汰；估值 unavailable；`json.dumps(allow_nan=False)` 通过 |
| 休市 两层都合法 | 仍返回文件值（48.0），`_asof` 为文件时间，0 次上游 |
| 交易时段 合法内存 | 内存优先，0 次上游，无 fallback 标记 |
| 交易时段 非法内存 + 合法文件 | 返回文件值，`_asof` 为文件时间，上游 1 次 |
| force + 上游成功 | 返回新数据，无 fallback，上游 1 次 |
| force + 上游失败 + 非法文件 + 合法内存 | 回退内存，`_asof` 保留，上游 1 次 |
| force + 上游失败 + 合法文件 | 返回文件值（既有语义） |
| 隔离 | 只清 `fin_600519`；`fin_000001` / `sector_flow` / `__data_meta__` 原样 |

### 15.5 诊断通道（未变）

`_FIN_LAST_DIAG` 仍是模块级最新值，**不具备逐请求绑定能力**。
S3-4B 不得直接接入页面，必须按本次响应的 `served` + 实际返回值现场生成状态对象（见 §14.5）。
本轮新增的 `memory_fallback` 只是内部排查标签，同样不构成页面状态契约。

### 15.6 剩余风险

- 内存回退的时间可能很旧（休市后隔夜），页面必须显示 `_stale` 与原始时间，不能当"刚更新"。
- 内存条目进程重启即消失：极端情况下（重启 + 文件损坏 + 上游不可达）仍会返回 `None`，这是正确的降级。
- 回退不触发额外上游请求，但也不修复坏文件之外的其它缓存层。
