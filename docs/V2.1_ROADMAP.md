## 2. 方向 D1：代码架构渐进式升级

### 2.1 当前问题

1. `data_service.py` 同时是"缓存层 + HTTP 客户端 + 业务组装 + 降级策略 + 指标统计"。
   典型症状：想给缓存加 TTL 淘汰，必须改动取数文件；想换数据源，必须改业务函数。
2. `_cached_get(cache_key, fetcher, validate_fn, source, ttl, force)` 6 个参数，
   把缓存策略和业务语义耦在字符串 key 上（`f"stock_quote:{code}"` 这种隐式契约）。
3. 取数函数直接返回"页面要的形状"，导致同一份原始数据被不同页面各自拼装。
4. `routes.py` 里参数校验散落，`code` 的正则校验重复 10+ 次。
5. 没有 Provider 概念：腾讯、东财、F10、DeepSeek 各写各的，失败语义不统一。

### 2.2 目标架构

```
providers/            # 只负责"取原料"，不做业务判断，返回统一 RawResult
  base.py             #   RawResult(ok, data, error, elapsed_ms, endpoint, fetched_at)
  tencent.py          #   行情 quotes
  eastmoney.py        #   资金流 / 板块 / 行业PE / F10
  deepseek.py         #   AI（可选，无 key 时 available=False）
  registry.py         #   name -> provider，按优先级 + 健康度选择
services/             # 业务装配，输入 Provider 结果，输出页面契约
  quote.py  flow.py  valuation.py  policy.py  health.py
cache/
  store.py            # JSON 文件 + 内存两层，键名与 TTL 显式声明
  keys.py             # 所有 cache key 的唯一声明处（不再散落 f-string）
web/
  routes/             # 按页面拆 blueprint：dashboard, flow, valuation, ai, health
  validators.py       # stock_code / industry / live 等统一校验
```

**渐进原则（硬约束）**：

- 一次只搬一个模块，搬完合并；
- 旧函数保留为**兼容垫片**（`data_service.get_stock_valuation` 内部转调
  `services.valuation.get_stock_valuation`），页面与旧测试零改动；
- 每搬一个模块，409 个测试必须全绿才允许进下一步；
- 不新建框架、不引入依赖（requirements.txt 保持 flask + requests）。

### 2.3 拆分顺序（每步都可独立回滚）

| 步 | 搬什么 | 为什么先搬它 |
|---|---|---|
| S1 | `cache/store.py` + `cache/keys.py` | 无业务语义，纯搬运，风险最低；搬完其他人才能用显式 key |
| S2 | `providers/base.py` + `providers/tencent.py` | 行情是绝大多数页面的入口，先统一返回值 |
| S3 | `providers/eastmoney.py`（资金流、行业 PE、F10） | 覆盖资金与估值两条链路 |
| S4 | `services/flow.py`、`services/valuation.py` | 依赖 S2/S3，此时才有"装配层"可写 |
| S5 | `web/routes/*` 拆 blueprint + `validators.py` | 纯路由层搬动，用现有路由测试做回归 |
| S6 | `services/policy.py`（把 `policy_live` / `events_store` 的页面侧装配收进来） | 政策相关最敏感，放最后 |
| S7 | `providers/deepseek.py` + `services/ai.py` | 可选链路，失败不影响主页面 |

### 2.4 预期修改文件

新增：`cache/{__init__,store,keys}.py`、`providers/{__init__,base,tencent,eastmoney,deepseek,registry}.py`、
`services/{__init__,quote,flow,valuation,policy,health,ai}.py`、`web/{__init__,validators}.py`、
`web/routes/{__init__,dashboard,flow,valuation,ai,health}.py`。
修改：`data_service.py`（保留薄垫片）、`routes.py`（改为注册 blueprint）、`app.py`、`data_health.py`。
测试：新增 `tests/test_providers_contract.py`、`tests/test_cache_keys.py`、`tests/test_routes_blueprints.py`。

### 2.5 验收标准（每一步都要满足）

1. `python3 -m unittest discover -s tests` 全绿（数量只增不减）；
2. 所有既有 URL 与响应 JSON 字段**逐字不变**（用现有 `test_routes_offline.py` +
   `test_ui_contract.py` 做快照）；
3. 旧入口仍可调用：`data_service.get_market_flow()` 等在原位可用（垫片有独立单测）；
4. 页面手工过一遍 6 个入口不报错（**真实浏览器**，本轮不算，因为要人肉看）；
5. 单步 diff 内业务逻辑零改动（只搬代码 + 改 import）。

### 2.6 兼容性与回滚

- 兼容：垫片 + 双写期（新模块与旧函数都可用），旧函数标记 `# TODO(v2.1): remove in v2.2`；
- 回滚：每步独立 commit，`git revert <该步>` 即可；不涉及数据库，无数据迁移风险。

## 3. 方向 D2：历史估值分位

### 3.1 当前问题

- 现在只有"当前 PE vs 行业 PE"和内在价值估算（`estimate_intrinsic_value`），
  **没有任何历史区间**：缺 3 年 / 5 年 PE、PB 序列。
- 现有数据源（腾讯行情、东财 F10）只给当前快照，历史 PE 需要"历史股价 + 历史每股收益"
  自己算，或用带历史估值的接口；两条路都必须留痕（口径写清楚，不许两种口径混用）。
- 页面当前明写"未接入"，这是对的 —— 一旦做，就必须有真实数据支撑，不能拿当前值反推。

### 3.2 目标设计

```
valuation_history(code, trade_date, pe_ttm, pb, eps_used, price_used, source, fetched_at, calc_version)
    PRIMARY KEY (code, trade_date)
```

- **口径统一（硬约束）**：同一只股票同一 day 只允许一套口径；
  `calc_version` 记录算法版本（如 `eps_ttm_v1`）；换口径必须换版本号并重算，不允许新旧混排。
- 分位算法：`percentile = count(x <= current) / count(all)`（含当前值，口径写进返回体）；
  区间固定 3 年（750 交易日）与 5 年（1250 交易日），按**交易日**而非自然日切。
- 数据不足：样本 < 250 个交易日 → 返回 `insufficient_sample`，页面显示"数据不足（样本 N 天）"，
  **不给分位数字**。
- 异常值：PE <= 0（亏损）单独标记，不参与分位；|z| > 5 的极端值保留但标注 `outlier=true`
  （删除历史极值等于篡改历史，宁可标出来）。
- 估值分位只在个股估值页出现，跟随所选个股。

### 3.3 实施步骤

1. **先解决数据来源**（这是本方向真正的难点，不是画图）：
   - 路线 A：日线收盘价（现有 `get_index_history` 同源可取个股历史）+ 各期 TTM EPS 序列
     （财报发布日期对齐，避免前视偏差 use-only-published-data）；
   - 路线 B：找提供历史 PE/PB 的公开接口（需验证稳定性和字段口径）。
   - 先写一个**数据可得性探针脚本** `scripts/valuation_probe.py`，输出实测能拿到多少天、
     字段名、缺失率；拿不到就到此为止，不做假分位。
2. 建表 + `services/valuation_history.py`（拉取、落库、补齐、断点续抓，限速）。
3. 计算分位（纯函数，好测）：`percentile_rank(series, current)`。
4. 接口：`GET /api/valuation-percentile?code=...&years=3|5`，**对齐日期后**返回
   `{pe:{current,pct,sample,insufficient_sample,outliers}, pb:{...}, asof, calc_version}`。
5. 页面：个股估值页新增"历史分位"卡片，缺数据显示原因，不显示 0%。

### 3.4 预期修改文件

新增：`services/valuation_history.py`、`scripts/valuation_probe.py`、
`tests/test_valuation_percentile.py`、`tests/test_valuation_history_store.py`、
`static/js/valuation_percentile.js`。
修改：`routes.py`（新接口）、`templates/valuation.html`、`config.py`（区间常量）、`README.md`。

### 3.5 验收标准

1. 探针脚本能实测输出可获取的交易日数量与缺失率（**数据不足就先不做后端**）；
2. 分位纯函数单测：单调性、含当前值口径、样本不足、全亏损序列、极端值标注；
3. 同一股票两种口径不会同时出现在一条记录里（`calc_version` 单测）；
4. 数据不足时接口返回 `insufficient_sample` 且页面不显示分位数字；
5. 断网/接口失败 → 明确 `unavailable`，不回退到"用当前值假装分位"。

### 3.6 兼容性与回滚

- 新表、新接口、新卡片，**不动现有估值字段**；
- 回滚：隐藏卡片 + 停用接口即回到 V2.0.x 行为；`valuation_history` 表独立，删表无副作用。

## 4. 方向 D3：政策全文与个股影响分析

### 4.1 当前问题（部分实现）

已有：标题、摘要、方向、来源、关联标的、静态策池、快讯半自动采集、个股画像关键词+出处、
两源检索与四档状态。
缺：**政策原文本体**、条文要求识别、主营业务→收入/成本/利润的传导机制、证据链留存。

### 4.2 目标设计

```
policy_documents(doc_id PK, title, publisher, doc_no, publish_date, url, raw_text,
                 content_sha256 UNIQUE, fetched_at, source_grade, status)
policy_doc_links(doc_id, event_id, relation)          # 原文 ↔ 事件
policy_analysis(doc_id, code, model, prompt_version, analyzed_at,
                requirement, revenue_impact, cost_impact, profit_impact,
                certainty, evidence_json, review_status, reviewer, reviewed_at)
```

- **一手来源优先**：部委/交易所/公司公告（`source_grade=primary`）> 财经媒体（`secondary`）>
  聚合快讯（`tertiary`）。`tertiary` 不得单独支撑"机制"结论。
- 抽取分两段，**不许一步到位出结论**：
  1. 事实抽取：文号、发布机关、生效日期、适用对象、明确要求（逐条，带原文定位偏移）；
  2. 影响推演：主营业务关联（来自 `stock_profile._terms_with_evidence` 的真实经营范围）
     → 产业链位置 → 收入/成本/利润三条路径，每条必须引用原文片段。
- 结论分级：`直接相关 / 间接相关 / 无法判断`；`无法判断` 必须允许存在，**不许凑结论**。
- 人工审核：`review_status` 只有人能置 `approved`；AI 产出永远 `pending`。
- 展示位置不变：只在个股估值的政策区块，跟随所选个股。

### 4.3 实施步骤

1. `policy_documents` 表 + 原文抓取（单域名限速、robots 尊重、失败记 `fetch_failed`）；
2. 正文抽取与去重（`content_sha256`），保留 `raw_text` 与抓取时间；
3. 事实抽取（规则 + 模型双路，交叉不一致标 `conflict`）；
4. 影响推演（严格模板：每条影响必须挂 `evidence_json` 里的原文片段偏移）；
5. 审核流：CLI `policy review --id N --approve|--reject`，页面显示审核人/时间；
6. 个股侧聚合：按 `policy_doc_links` 挂到当前个股，缺原文时降级为现行为（标题+摘要）。

### 4.4 预期修改文件

新增：`services/policy_docs.py`（抓取+抽取）、`services/policy_impact.py`（推演+证据校验）、
`tests/test_policy_doc_extract.py`、`tests/test_policy_impact_evidence.py`。
修改：`events_store.py`（建表迁移）、`policy_live.py`（接原文）、`routes.py`、`templates/valuation.html`、
`scripts/events_cli.py`（review 子命令）。

### 4.5 验收标准

1. 同一条原文重复抓取不产生新行（`content_sha256` 唯一约束单测）；
2. 事实抽取输出必须带原文偏移，偏移指回 `raw_text` 后字符串一致（**证据可校验**）；
3. 影响推演的每条结论都能在 `evidence_json` 找到出处，找不到即拒收（单测覆盖"AI 编造证据"）；
4. 无原文时行为与 V2.0.2 一致（降级不报错）；
5. 人工审核状态不被任何自动流程改写（沿用 seed 事务修复里的保护语义）。

### 4.6 兼容性与回滚

- 新表 + 新字段，旧事件照常显示；`policy_analysis` 空表时页面走旧路径；
- 回滚：停用 `policy_docs` 抓取 + 关闭原文区块，回到标题+摘要。

## 5. 方向 D4：AI 分析记录持久化

### 5.1 当前问题

`ai_analysis.py` 只把结果写进 `ai_cache.json`（按输入 key 覆盖），
**没有股票维度的时间线**：不知道某次分析用了哪天的数据、哪个模型版本，无法复盘。

### 5.2 目标设计

```
ai_analysis_runs(
    id PK,
    code, analysis_type,          # 个股诊断 / 政策影响 / 估值解释
    model, model_version,          # 模型名 + 版本/快照标识（DeepSeek 返回的 model 字段）
    prompt_version,                # 模板版本，改模板必须升版本
    analyzed_at,                   # 分析时间
    data_asof,                     # 数据截止日期（行情/财报的 as-of，不是今天）
    snapshot_id,                   # 数据快照指纹（行情+财报关键字段的 sha1）
    input_json,                    # 实际喂进去的输入（可脱敏但结构完整）
    result_json,                   # 结构化结论（不是一段文字）
    evidence_json,                 # 引用证据（字段名+取值+来源+时间）
    tokens_in, tokens_out, cost_estimate,
    status                         # ok / failed / rejected_by_review
)
```

- **不只存一段文字**：`result_json` 必须是结构化的（观点/依据/风险/不确定性分字段）；
- 同一 `snapshot_id + prompt_version + model` 视为同一次分析，重复请求复用不重复入库；
- 查询：`GET /api/ai-history?code=...&limit=20`，支持按日期区间与模型筛选；
- 复盘：同一股票两次分析可对比（哪些结论变了、数据变了没有）。

### 5.3 实施步骤

1. 建表 + `services/ai_runs.py`（写入、查询、去重）；
2. `ai_analysis.py` 改造：返回结构化结果 + 元信息（模型、data_asof、snapshot_id）；
3. `ai_cache.json` 降级为纯性能缓存（可按 key 删除，不影响历史）；
4. 接口与页面：个股 AI 分析页加"历史分析"列表，点开看单次详情与证据；
5. 对比视图（可选，最后做）：两次分析的 diff。

### 5.4 预期修改文件

新增：`services/ai_runs.py`、`tests/test_ai_runs_store.py`、`tests/test_ai_history_api.py`、
`static/js/ai_history.js`。
修改：`ai_analysis.py`、`routes.py`、`templates/ai.html`、`data_health.py`（"有 N 条记录"）。

### 5.5 验收标准

1. 写入一条记录后，重启进程仍可查到（真实 SQLite 校验，不看内存）；
2. 无 key / 调用失败也留痕（`status=failed` + 错误摘要），**不静默丢弃**；
3. `snapshot_id` 相同的重复请求不产生第二条记录；
4. `data_asof` 必须来自数据本身，缺失时写 `unknown` 而非今天；
5. 历史记录不被新分析覆盖或删除（只增）。

### 5.6 兼容性与回滚

- 新表；`ai_cache.json` 行为保留，无记录时页面显示空列表而非报错；
- 回滚：关闭"历史"入口，缓存路径仍可用。

## 6. 方向 D5：数据源成功率持久化

### 6.1 当前问题

`data_service.SOURCE_STATS` 是模块级 dict（`calls/ok/fail/ms_total/last_ok/last_error`），
重启清零 → 健康面板的"成功率"只代表本次运行，无法回答"这个源最近一周稳不稳"。

### 6.2 目标设计

```
data_source_events(id PK, source, ts, ok, ms, error, endpoint, cache_hit)
data_source_stats(source PK, window_date, calls, ok, fail, ms_p50, ms_p95,
                  last_ok_at, last_error, last_error_at, updated_at)
```

- 写入：每次 `record_source()` 追加一条 `events`（轻量，判重/采样可配），并 upsert 当日 `stats`；
- **不阻塞主链路**：写失败只记日志，绝不让监控拖垮取数（现有"单模块失败不牵连全局"原则）；
- 保留期：`events` 保留 30 天滚动清理，`stats` 永久（按天一行，体量可控）；
- 查询：`GET /api/data-health` 增加 `history` 段（近 7/30 天成功率、p50/p95、最后成功时间、
  最近错误），数据来源标注"来自本地统计库"。

### 6.3 实施步骤

1. 建表 + `services/source_stats.py`（append + upsert + 查询 + 清理）；
2. `record_source()` 接持久化（try/except 包裹，失败静默记日志）；
3. `data_health._sources_row()` 改为读历史表，进程内统计降级为兜底；
4. 首页健康卡片增加"近 7 天成功率"与"最后成功时间"两列；
5. 数据质量异常检测（最后一条：成功率骤降/连续失败）。

### 6.4 预期修改文件

新增：`services/source_stats.py`、`tests/test_source_stats_persist.py`、
`tests/test_data_health_history.py`。
修改：`data_service.py`（`record_source`）、`data_health.py`、`routes.py`、`static/js/app.js`、
`templates/dashboard.html`。

### 6.5 验收标准

1. 记录后进程重启，历史成功率仍在（真实文件库校验）；
2. 数据库写失败时取数链路照常返回（注入异常单测：`record_source` 抛错不影响结果）；
3. `p50/p95` 计算有单测（含空样本、单样本）；
4. 30 天清理不误删当日数据；
5. 健康快照仍**零外部请求**（只读本地库）。

### 6.6 兼容性与回滚

- 新表；健康面板字段只增不改；
- 回滚：`record_source` 关掉持久化开关，行为回到内存统计。

## 9. 兼容性与回滚总则

1. **接口只增不改**：新字段加进去，旧字段不变；前端按可选字段渲染。
2. **页面入口只增不删**：新卡片失败时隐藏，不阻塞整页。
3. **表只加不删**：新表独立；需要改结构时加列 + 回填，不重建。
4. **每阶段一个可独立 revert 的提交**；提交信息写清阶段号（`v2.1/S1: ...`）。
5. **回滚演练**：每阶段交付前，用 `git revert` + 停服务 + 重启验证一次能回退到上一阶段。
6. **禁止**：`push --force`、`reset --hard`、删远程分支、删本机数据库。
