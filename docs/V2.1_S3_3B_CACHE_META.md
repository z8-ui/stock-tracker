## 1. 旁路元数据格式

### 1.1 存储位置

```json
{
  "sector_flow":      {"__data": [ ... 496 条 ... ], "fetched_at": 1762...},
  "sector_valuation": {"__data": [ ... 496 条 ... ], "fetched_at": 1762...},
  "__data_meta__": {
    "sector_flow":      { "schema": 1, "...": "..." },
    "sector_valuation": { "schema": 1, "...": "..." }
  }
}
```

为什么不另开一个文件：数据与元数据必须能一次原子替换（否则崩溃后会出现"新数据 + 旧元数据"），
且现有测试通过 patch `_load_cache/_save_cache` 隔离缓存 —— 同一份文件让隔离自动生效，
测试元数据不会写进真实目录。业务 key 的信封一个字节都没改，旧版本读这份文件不受影响。

### 1.2 字段表（`schema = 1`）

| 字段 | 类型 | 含义 | 缺失时 |
|---|---|---|---|
| `schema` | int | 元数据格式版本 | — |
| `cache_key` | str | 对应的业务 key | — |
| `mode` | str | `flow` / `valuation` | — |
| `source` | str | `eastmoney_sector` | `""` |
| `fetch_status` | str | 产生这份数据的抓取结果：`success` / `failed` / `not_attempted` | `unknown` |
| `completeness` | str | `complete` / `partial` / `unknown` | `unknown` |
| `rows` | int | 落盘时的行数 | `None` |
| `total` | int/null | 上游 `total`（板块总数） | `None` |
| `missing_pages` | list[int] | 失败的分页号 | `[]` |
| `missing` | list[str] | 缺失项：`"5"`、`"duplicates:N"`、`"rows_mismatch:a!=b"`、`"total_mismatch:pn:a!=b"` | `[]` |
| `duplicates` | int | 去重掉的重复行数 | `0` |
| `notes` | list[str] | 解析事实：`negative_pe:90`、`pb_unavailable:496`、`skipped_no_name:N`、`mock_fallback` | `[]` |
| `fetched_at` | float | 本地抓取时刻（epoch） | — |
| `asof` | str | 上游数据时间；板块 clist **没有时间字段** → 恒 `""` | `""` |
| `asof_source` | str | `upstream` / `unknown` | `unknown` |
| `is_mock` | bool | 是否模拟兜底数据 | `false` |
| `data_hash` | str | `sha256:<hex>`，规范 JSON（sort_keys + 紧凑分隔符） | `""` |
| `written_at` | float | 元数据写入时刻 | — |

示例（真实 496 条估值）：

```json
{
  "schema": 1, "cache_key": "sector_valuation", "mode": "valuation",
  "source": "eastmoney_sector",
  "fetch_status": "success", "completeness": "complete",
  "rows": 496, "total": 496,
  "missing_pages": [], "missing": [], "duplicates": 0,
  "notes": ["negative_pe:90", "pb_unavailable:496"],
  "fetched_at": 1762..., "asof": "", "asof_source": "unknown",
  "is_mock": false, "data_hash": "sha256:...", "written_at": 1762...
}
```

### 1.3 写入规则

- 只在 `_store()`（前台抓取）和 `_spawn_refresh()`（后台 SWR）里写，二者调用同一个 `meta_fn`。
- 元数据生成失败（异常）→ 不写元数据，但**不影响业务数据写入**；该数据下次读取时因
  "无可信元数据"降级为 `unknown`。
- 模拟数据（`ALLOW_MOCK_FALLBACK=True`）永远 `fetch_status=not_attempted`、
  `completeness=unknown`、`notes=["mock_fallback"]`，不会标成 complete。

### 1.4 读取与校验（`data_meta(cache_key, served_from, trace)`）

| 情况 | `meta_status` | completeness / freshness |
|---|---|---|
| 元数据不存在 | `missing` | `unknown` / `unknown`（本次抓取失败退回 → `stale` + `failed`） |
| 数据不存在 | `missing` / `orphan` | `unknown` |
| schema 不是 1 | `schema` | `unknown`，`missing=["meta:schema_unsupported"]` |
| hash 不一致 | `mismatch` | `unknown`，`missing=["meta:hash_mismatch"]` |
| 元数据 `fetched_at` 与缓存条目对不上 | `fetched_at` | `unknown`，`missing=["meta:fetched_at_mismatch"]` |
| 写盘失败（本次数据没落盘） | `not_persisted` | `unknown`，`missing=["meta:not_persisted"]` |
| 四项都通过 | `ok` | 取元数据；`complete` 但行数≠total 时防御性降为 `partial` |

可信性判定只有一个入口 `_meta_trust()`（schema + hash + fetched_at），
`data_meta()` 与 `_needs_legacy_migration()` 共用 —— 不允许一处放宽、一处从严。

`freshness` 只看时间：`file_fallback` → `stale`；有 `fetched_at` → 盘中按 `STALE_AFTER_SEC`、
休市按 3 天判定；否则 `unknown`。

`fetch_status` 描述"产生当前数据的抓取"，但本次请求抓取失败时覆盖为：
- `served_from == file_fallback` → `failed`
- 无缓存且上游抛错 / Provider 返回 failed → `failed`
- Provider 返回 empty → `empty`
（`served_from` 单独记录本次请求的数据来源，两者不混用。）

## 2. 旧 60 行缓存迁移方案

**判据（不用行数阈值）**：`data` 存在且不存在"`data_hash` 与当前数据一致"的元数据。

**动作**：

1. 标记 `_LEGACY_MIGRATION_AT[key] = now`，发起**一次**强制刷新（`_cached_get(force=True)`，
   休市也执行）——这就是"一次性失效/安全刷新"策略。
2. 刷新成功 → 写入真实全量数据 + 元数据 → `complete`（或 `partial`）。
3. 刷新失败 → 返回旧数据；元数据保持 `missing`，对外 `completeness=unknown`、
   `freshness=stale`、`fetch_status=failed`。**不删旧缓存、不补行数、不猜完整。**
4. 冷却 `LEGACY_MIGRATION_INTERVAL = 1800s`：冷却内不再打上游，避免每个请求都抓 5 页；
   进程重启后冷却清零，会再试一次（期望行为）。
5. 合法的 5 行测试缓存与 60 行旧缓存走**同一条**逻辑：不会被删，只在一次成功刷新后
   被真实数据替换。

**有元数据时的行数语义**（任务 2 要求）：

| 元数据 | 对外 |
|---|---|
| `rows == total` | `complete` |
| `rows < total` | `partial` |
| 无元数据 | `unknown`（绝不 complete） |

## 3. HTTP Headers 契约

响应头（两个接口都带，失败响应也带）：

| Header | 取值 | 缺失编码 |
|---|---|---|
| `X-Data-Fetch-Status` | `success` / `failed` / `empty` / `not_attempted` / `unknown` | `unknown` |
| `X-Data-Completeness` | `complete` / `partial` / `unknown` | `unknown` |
| `X-Data-Freshness` | `fresh` / `stale` / `unknown` | `unknown` |
| `X-Data-Meta-Status` | `ok` / `missing` / `mismatch` / `orphan` | `missing` |
| `X-Data-Rows` | 整数 | `unknown` |
| `X-Data-Total` | 整数 | `unknown` |
| `X-Data-Fetched-At` | `YYYY-MM-DD HH:MM:SS`（本地抓取时刻） | `unknown` |
| `X-Data-AsOf` | 上游数据时间；板块接口无时间字段 | `unknown` |
| `X-Data-Served-From` | `network` / `memory` / `stale` / `file` / `file_fallback` / `none` | `none` |
| `X-Data-Missing` | 逗号分隔，如 `3,5,duplicates:100` | `-`（无缺失） |

- `X-Data-Fetched-At` 是**本地抓取时刻**，`X-Data-AsOf` 才是上游数据时间；
  板块接口没有时间字段，所以 `X-Data-AsOf` 恒为 `unknown` —— 不拿本地时间冒充交易所时间。
- 同时设置 `Access-Control-Expose-Headers`（上面 10 个名字），浏览器跨域可读。
- JSON 主体不变：`/api/heatmap` 仍是 `{code, data, _market_status, is_mock, is_stale, asof, stale_reason}`，
  `data` 是 list；`/api/sector-valuation` 仍是 `{code, data, is_mock}`。

## 7. r1 复审整改（GPT PASS-with-must-fix）

复审结论：PASS-with-must-fix，S3-3B 暂不关闭。三项必改 + 一处行尾空格。

### 7.1 必改 1：旧元数据可能被错误复用

问题：`meta_fn` 抛异常时 `_cache_update(meta=None)` 只更新业务数据、保留旧元数据；
若新旧数据内容相同（hash 相同），旧记录继续被信任，旧的 `complete` 被用到新一轮数据上。
另外 schema=999 也会被判 `ok`。

整改：

1. 新增 `_meta_trust(record, data, fetched_at)` 作为**唯一**可信性判定：
   `schema == 1` 且 `data_hash` 匹配 且 元数据 `fetched_at` 与缓存条目一致。
2. `meta_fn` 异常或返回空 → `_cache_update(..., drop_meta=True)`，
   **同一次**读-改-写里删掉该 key 的旧元数据（不留"新数据 + 旧元数据"）。
3. `data_meta()` 与 `_needs_legacy_migration()` 共用 `_meta_trust()`；
   迁移不再只比 hash —— schema 不对或时间对不上同样触发一次性安全刷新。
4. 新增 `meta_status`：`schema` / `fetched_at`（另有 `not_persisted`，见 7.2）。

测试：`tests/test_s3_3b_fix_r1.py::TestMetaReuse`（6 例），覆盖同内容新一轮、
时间对不上（GPT 复现）、schema 不支持、失效后重启仍 unknown、迁移判据、整链路。

### 7.2 必改 2：写盘失败导致响应与 Headers 不对应

问题：`_save_cache()` 吞掉写入异常。内存已是 NEW、磁盘仍是 OLD，
路由用 `data_meta()` 读磁盘，Headers 描述的是 OLD，与本次返回的 NEW 不一致。

整改：

1. `_save_cache()` / `_cache_update()` 返回写盘结果；失败时旧文件原样保留
   （tmp + 原子替换），不破坏已有合法缓存。
2. `_store()` 把结果写入 `trace["persisted"]`；路由把**本次实际返回的数据**
   传给 `data_meta(data=...)`。
3. 写盘失败 → `meta_status=not_persisted`、`completeness=unknown`、
   `freshness=unknown`、`Rows` 按本次返回数据如实报。
4. 其它模块调用 `_cache_update` 不传新参数，行为不变（返回值被忽略即可）。

测试：`TestWriteFailure`（5 例），含磁盘异常、返回 NEW/磁盘 OLD、恢复后重新可信、
不影响其它 key。

### 7.3 必改 3：JSON `is_stale` 与 `X-Data-Freshness` 矛盾

问题：真实证据里 Headers 是 `stale/failed/file_fallback`，JSON 却是 `is_stale=false`
（旧 JSON 只看年龄，新 Headers 把"失败后退回旧缓存"判为 stale）。

整改（方案 A：统一语义，键集合不变）：

`is_stale = 本次返回的数据不能被当作新鲜可用`

1. `file_fallback`（本次抓取失败退回旧缓存）→ `true`，原因写明"上游抓取失败"；
2. 元数据可信但过期 → `true`；
3. 无法确认新鲜度（元数据 missing/schema/mismatch/fetched_at/not_persisted）→ `true`；
4. 其余按 `cache_meta()` 的年龄口径。

实现：`routes._staleness_from_meta(meta, cm)`，JSON 键仍是
`is_stale` / `stale_reason` / `asof`，只是取值与 Headers 同源。

测试：`TestStaleConsistency`（5 例），每条都断言
`body.is_stale == (X-Data-Freshness != "fresh")` 这一不变量。

`data_service.py` 中 `_finish()` docstring 的尾随空格已清理，`git diff --check` 通过。
