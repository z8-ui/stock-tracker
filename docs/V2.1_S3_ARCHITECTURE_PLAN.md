### 3.2 为什么以 `eastmoney_flow.py` 为参考，而不是重写契约

- 它已经证明三模式共存可行：`history`(daykline) / `today`(kline) / `market_snapshot`(ulist.np)，
  **同一 Provider 不同报文结构，不强行统一解析器**（`_parse_klines` vs `_parse_ulist`）。
- 它把"元→亿"和"缺字段"处理留在 Provider 内，上层只拿领域值。
- 它证明了"Provider 不做缓存"是可行的：三层缓存仍在 `_cached_get`，Provider 无状态。

因此 S3 的统一只做三件事：**信封统一、错误语义统一、工具集中**；
**不统一各源的业务载荷形状**（腾讯行情仍是字段列表→dict，F10 仍是报告期结构，板块仍是 list）。

### 3.3 统一证券身份（Q 决策后新增，取代"一个通用 secid 函数"）

`normalizers.py` 不提供"万能转换函数"，而是先建立与数据源无关的身份三元组，再逐源转换：

```python
SecurityId(code="600519", exchange="SH", security_type="stock")
# exchange: SH / SZ / BJ        security_type: stock / index / b_share
to_eastmoney_secid(sid)   # -> "1.600519" / "0.000001" / "0.830799"
to_tencent_symbol(sid)    # -> "sh600519" / "sz000001" / "bj830799"
```

理由：
- 现有代码把"市场判定"散在 6 处（TD-08），每处都在猜：`startswith("6")` 之类规则
  对**沪市B股（900xxx）**、**指数（000001 既是深成指也是平安银行）**、**北交所（8/4/920 开头）**
  分别会给出不同错误答案；
- 东财 secid 与腾讯 symbol 的市场号规则不同（东财 1=沪 0=深，北交所在东财属 0 但腾讯用 bj），
  强行统一成一个字符串必然有一边要再解析回来。

**必须独立测试的三个边界**（S3-1 随行落地，不在 S3-0 实施）：
1. 沪市 B 股 `900901` → 东财 `1.900901` / 腾讯 `sh900901`（不是 `0.`）；
2. 指数 `000001` 在 `security_type="index"` 时 → 东财 `1.000001`、腾讯 `sh000001`，
   而 `security_type="stock"` 时 → 东财 `0.000001`、腾讯 `sz000001`；
3. 北交所 `830799` / `920xxx` → 腾讯 `bj830799`；东财侧若资金流接口本身返回 500，
   维持 Q6=B（记为已知限制，不编造第二个源）。

### 3.4 公共 HTTP 请求层（S3 后续阶段共用的唯一出网点）

新增薄层（计划 `services/data/http.py`，S3-1 起用；不引入新依赖，仍是 `requests`）：

| 职责 | 归属 | 说明 |
|---|---|---|
| timeout / 重试策略（默认不重试） | 公共层 | 每 Provider 声明 `timeout`，公共层执行；禁止隐式重试放大上游压力 |
| HTTP 状态检查（4xx/5xx → `HttpError`） | 公共层 | 区分 4xx（参数/权限）与 5xx（上游故障），都映射 `failed` |
| JSON 解码（含编码判定） | 公共层 | 腾讯快照是 GBK 文本、其余是 UTF-8 JSON，编码由调用方声明 |
| 网络异常分类（DNS/连接/超时） | 公共层 | → `ProviderNetworkError` / `ProviderTimeout` |
| Session 管理（连接复用、UA/Referer 默认头） | 公共层 | 每源一套默认头，不为省 20 行代码在 Provider 里散写 |

**不做**：公共层不解析业务字段（不认 `f62`/`f9`/`parts[30]`），不猜备用数据源，
不把"失败"翻译成另一种数据形状。Provider 自己负责 URL、参数与业务报文解析。

## 4. Provider 契约 v2（计划，未实现）

### 4.1 现有契约（`services/data/base.py`）

```python
ProviderResult(data, source, status, asof, fetched_at, is_stale, error, elapsed_ms, attempts)
Provider.request(*args) -> raw            # 发请求
Provider.normalize(raw, *args) -> (data, asof)   # 解析
Provider.fetch(*args) -> ProviderResult    # 唯一入口，异常转状态
```

### 4.2 需要补的三点（都不破坏现有调用方）

1. **`partial` 必须能被 Provider 产出**
   现状：`fetch()` 只在 `data is empty` 时给 `empty`，否则 `success`；
   `STATUSES` 里有 `partial`，但**没有任何 Provider 产生它**（`base.py` L96-99 只算 success/empty）。
   S3 要求：`normalize()` 可返回 `(data, asof, extra)`，`extra` 含
   `partial: bool`、`missing: [字段或标的]`、`notes: [str]`、`source: str`；
   `fetch()` 据此把 status 置 `partial`。**S2-KI-1 的修复依赖这一条**（Q1=A 已定稿）。

   **四个词必须严格分开，不得互为同义词**（写进契约文档与代码注释）：

   | 词 | 含义 | 由谁产生 | 例子 |
   |---|---|---|---|
   | `partial` | 拿到了数据，但有明确缺失项（部分成功） | Provider（`extra`） | 3 个指数只回 2 个 → `partial` + `missing=["深证成指"]` |
   | `stale` | 数据本身过期（超出新鲜度窗口），但内容完整 | 缓存层 | 休市第 3 天仍显示上周五快照 |
   | `degraded` | 本次用的是降级来源（文件缓存兜底），上游请求失败 | 缓存层 | 断网时返回磁盘缓存 + `_served_from="file_cache"` |
   | `missing` | 具体缺了哪个字段/标的，是**明细数组**，不是一个状态 | Provider（`extra.missing`） | `["f23", "f37"]` 或 `["深证成指"]` |

   组合关系：`partial` 是业务结论；`stale`/`degraded` 是缓存可信度；
   可以同时出现（"降级的、部分的数据"），但**页面文案必须分别说明**，不能合并成一句"数据可能延迟"。

2. **`empty` 与"真实零值"必须由 Provider 明确区分**
   - `empty`：源返回了 0 条记录 → `data is None` 或 `[]`；
   - 真实零值：源返回了记录，字段值就是 0（如主力净流入 0）→ `success`，`data` 保留 0；
   - 禁止：字段缺失时补 0 后返回 success（`yuan_to_yi` 已对 None 抛 `ValueError`，保持）。
   S3 在契约文档写死这条，并为每个新 Provider 加"零值 vs 缺失"用例。

3. **原始报文可追溯，但不进内存常驻**
   新增可选字段 `raw_sha256: str`（默认空）与 `raw_bytes: int`；
   `TELEMETRY_DEBUG=1` 时才额外保留 `raw`（供排查），默认丢弃。
   理由：审查要求"能核对原文"，但把 8KB 报文塞进每个 ProviderResult 会污染缓存/日志。

### 4.3 明确不做的契约改动

- 不改 `ProviderResult` 的现有字段名与顺序（`as_dict()` 已对外）；
- 不让 Provider 返回"页面形状"（如 `{code:200,data:...}`）；
- 不引入泛型/ABC 继承树；`base.Provider` 保持 107 行的厚度；

## 5. 缓存架构（只提方案，S3 不先动 `_cached_get`）

### 5.1 现状风险（逐条对应任务书）

| 检查项 | 结论 | 证据 |
|---|---|---|
| 键是否含必要参数 | **否**：`stockflow_hist_{code}` 缺 `days` | `data_service.py:840` |
| 跨源缓存污染 | 现无（一个键一个源），但 `market_flow` 的日期来自腾讯、金额来自东财，**asof 混源** | L559 vs L571 |
| 过期策略是否合理 | 分层合理（盘中 TTL + SWR + 单飞；休市优先文件缓存），但"3 天"是自然日不是交易日 | L382 |
| 口径变化如何失效 | 只有 `market_flow` 靠 `_flow_fields_v` 自愈（L601/617），其余键只能等 TTL | L601 |
| 缓存是否记录来源+抓取时间 | dict 有 `_asof/_source/_stale`；**list 没有** | `_inject` L370、L492 注释 |
| 失败是否覆盖有效缓存 | 已被 `_refresh_is_valid` 四条规则挡住 | L207-229 |
| 降级是否伪装实时 | dict 有 `_stale/_stale_reason`；list 无标记 → 板块页可能把旧快照当实时 | L370、L499-504 |

### 5.2 提案（Q3=A 已定稿；信封归 S3-7A，键集中归 S3-7B）

1. **信封化**：落盘从"裸值"改为
   `{"v": 2, "data": ..., "asof": ..., "fetched_at": ..., "source": ..., "status": ..., "params": {...}}`
   —— list 也能带元数据；读旧格式时按现有路径包装，不丢数据。
2. **键集中声明** `services/data/cache_keys.py`：
   `stockflow_hist(code, days)`、`quote(code)`、`sector_flow()`、`sector_valuation()`、
   `fin(code)`、`industry_pe(code)`；每个键带 `version`（替代 `_flow_fields_v` 的业务自愈）。
3. **降级显式化**：降级返回必须带 `_served_from="file_cache"`、`_degraded=True`；
   页面（`static/js/app.js` 的健康/时间戳区）显示"缓存数据，非实时"。
4. **休市判定用交易日**：`_stale` 的 3 天上限改为"距最近交易日"，用 `market_calendar` 判定，
   不再用自然日差（周末+节假日组合会误判）。
5. **失败不写缓存**：保持现有 `_ok`/`_refresh_is_valid` 语义，不动。

> 硬约束：S3 阶段**不修改** `_cached_get` 的调用签名；信封化通过"读写适配"完成，
> 且必须先有 `tests/test_cache_envelope.py` 的读写兼容用例（旧文件→新读、新文件→旧读兜底）。

**实施顺序（Q3=A 定稿后的拆分）**：

| 子阶段 | 内容 | 位置 | 理由 |
|---|---|---|---|
| **S3-7A** | v2 信封 + 旧格式兼容 + list 基础元数据 + 原子写入 | **提到 S3-3 之前** | 没有 list `_asof/_stale`，S3-3 的板块页验收无法成立 |
| **S3-7B** | 键集中（补 `days`）+ `_degraded/_served_from` + S2-KI-1 + 交易日新鲜度 | 保持最后 | 跨所有模块，必须等 key 集合稳定；改键名会静默丢缓存，需要一次性收口 |

7A 的迁移动作只用"读写适配"：写新格式、读旧格式时在内存里包一层，
**不做一次性文件重写**（那会在断电时丢全部缓存）。旧备份 `_data_cache.json.bak-<时间>` 必须留在原位。

## 6. 异常与降级规范（S3 统一口径）

### 6.1 错误类型 → status → 页面（计划写死）

| 场景 | 异常类（`exceptions.py`） | Provider status | 界面 | 是否记故障 |
|---|---|---|---|---|
| 连接失败 / DNS | `NetworkError` | `failed` | 暂无数据 | 是 |
| 超时 | `TimeoutError`（Provider 内映射） | `failed` | 暂无数据 | 是 |
| HTTP 4xx/5xx | `HttpError`（S3 新增，区分 4xx/5xx） | `failed` | 暂无数据 | 是 |
| JSON/结构解析失败 | `FormatError` | `failed` | 暂无数据 | 是 |
| 必需字段缺失 | `FormatError`（带 field 名） | `failed` | 暂无数据 | 是 |
| 部分字段缺失 | 无异常，`extra.partial` | `partial` | 可用字段 + "部分数据" | 是（记 partial） |
| 源返回 0 条 | 无异常 | `empty` | 暂无数据（不是 0） | 否（休市时尤其） |
| 真实零值 | 无异常 | `success` | 显示 0 | 否 |
| 数据过期（缓存） | 缓存层标注 | `stale`（仅缓存层产生） | 数据显示 + 过期提示 | 否 |
| 未注册源 | `ProviderUnavailable` | `unavailable` | 功能不可用 | 否 |

### 6.2 硬规则

1. 禁止 `except: pass` 新增；已有 10 处按 S3 阶段逐一改成"记录 + 明确 status"
   （优先级见 TD-05）。
2. 禁止默认 0 / 空数组 / 默认涨跌幅（`data_service.py:735` 的 `-0.5` 必须消除）。
3. 禁止把"部分成功"当 `success`：任何缺失必须体现在 `partial` + `missing`。
4. 多源聚合（当前只有 `get_market_flow`）：任一侧缺失即不得组装成完整结论，
   已实现为返回 `None`（L583-584）；S3 不变更该语义，只把原因记进健康面板。

## 7. 数据健康与监控（S3 目标形态）

现状：`data_health.snapshot()`（`data_health.py:326`）读缓存 + `SOURCE_STATS` + Provider 遥测；

S3 要补的指标（不建表，先补字段）：

| 指标 | 来源 | 说明 |
|---|---|---|
| 每个源的 `last_success_at` | `_LAST_SUCCESS`（已有） | 现在没暴露给前端 |
| `data_asof` vs `fetched_at` 分开展示 | 缓存信封 | 现在只有 `_asof`，`fetched_at` 半隐 |
| `partial` 次数 | Provider 遥测扩展 | 现在只有 success/empty/failed |

| 新鲜度（交易日维度） | `market_calendar` | 现在用 3 自然日 |
| 数据日期是否落后于最近交易日 | calendar + `data.date` | 平台休市提示的关键 |

判定规则（写死，避免"周末=故障"）：

- 非交易日：不抓取不算失败；有最近交易日快照 → 展示 + 标日期 + 标休市；
- 非交易日 + 无缓存 → "暂无数据"，`status=empty`，不计入成功率分母；
- 交易时段失败 → 计故障；`success_rate` 只统计"发起过请求的窗口"。

持久化（D5 表）**不在 S3 实施**，作为 S4 候选；S3 只保证字段齐备、语义正确。

## 11. 一句话结论

S3 的价值不在"再多几个 Provider"，而在**把剩下 6 个仍在裸写 requests / 裸解析的数据模块
搬到统一边界上，同时把"缺失≠0、部分≠成功、缓存≠实时"三条语义落到契约和缓存层**；
规模上以 6 个小阶段、每阶段 ≤ 3 个文件、每阶段可独立 revert 为限。
